Conceito e protótipo · 2026-10-19

O sistema Delphi vira um contrato que o sistema novo tem de cumprir.

Migrar um sistema Delphi costuma falhar no mesmo ponto: ninguém sabe ao certo tudo o que ele faz. As regras estão espalhadas em telas, eventos de botão e SQL escrito dentro do código. A proposta é ler o sistema antigo e produzir, de forma automática e repetível, a lista do que ele promete ao usuário e ao banco de dados. Essa lista é o contrato. O sistema novo, em qualquer linguagem, é aceito quando cumpre o contrato.

Fonte Delphi (.pas, .dfm)→Contrato verificável→Sistema novo + testes de aceite

Como funciona

    
Quatro etapas, cada uma com uma prova

  

  

    
Extrair o contrato
pronto
A ferramenta lê units, formulários (em texto ou no formato binário do Delphi) e o SQL dentro do código. Mesma entrada, mesmo arquivo de saída, byte a byte, sem data nem caminho de máquina.

    
Fechar as pendências com quem conhece o sistema
pronto
O que a leitura não consegue afirmar vira pendência explícita: botão ligado a uma rotina sem código, SQL montado com variável, tela sem unit. Nada fica escondido; a conversa com o cliente parte dessa lista.

    
Conferir que o contrato ainda é o do sistema
pronto
O verificador refaz a leitura e compara seção por seção. Se alguém editou o contrato à mão ou o código mudou depois, ele aponta onde. Experimente na aba Verificar do protótipo.

    
Gerar os testes de aceite do sistema novo
próximo passo
Cada operação do contrato vira um teste: dado o clique em Salvar com estes campos, o banco recebe este INSERT nesta tabela. O sistema novo é entregue quando passa em todos.

  






  

    
O que já está de pé

    
    
      
  • Leitura de Object Pascal: classes, métodos, propriedades, regras com assinatura, registros e enumerações.
    • 
      
  • Formulários .dfm em texto e binário, com componentes, ligações de dados e eventos.
    • 
      
  • SQL dentro do código e dos componentes, com tabelas e parâmetros.
    • 
      
  • Cada clique ligado ao SQL que ele alcança, inclusive por rotinas chamadas e consultas abertas.
    • 
      
  • Sem o código-fonte, direto do executável (.exe, .dll): telas, componentes, eventos e SQL, sem rodar o programa.
    • 
      
  • Para ir além das telas no executável: engenharia reversa com o REA (código aberto, licença MIT), em versão fixa.
    • 
    

  

  

    
Limites conhecidos

    
    
      
  • Diretivas de compilação ({$IFDEF}) não são avaliadas: os dois ramos entram no contrato.
    • 
      
  • Chamadas entre rotinas são achadas pelo nome; o contrato mostra a lista para conferência.
    • 
      
  • SQL montado em tempo de execução vira pendência: a tabela real só aparece rodando o sistema.
    • 
      
  • Do executável sai tudo da tela, mas não o código de cada botão: ligar o clique ao SQL exige o fonte ou o REA.
    • 
      
  • Testado num projeto de exemplo e num executável montado a partir dele; o primeiro sistema real vai medir a cobertura de verdade.
    • 
    

  






  
Piloto com um cliente

  
Do que precisamos para rodar no primeiro sistema real

  

    
O cliente entrega
  • O código-fonte de um módulo (as pastas com .pas, .dfm e .dpr) ou, se o fonte se perdeu, só o executável.
  • Se possível, o esquema do banco (para cruzar tabelas e colunas).
  • Uma pessoa que conheça o sistema para fechar as pendências.

    
O cliente recebe
  • O contrato do módulo, em JSON e em relatório legível.
  • A lista de pendências, com arquivo e linha de cada uma.
  • Números medidos: telas, eventos, operações, tabelas e quanto está coberto.
  • A base para os testes de aceite do sistema novo.

  

  
O código do cliente é só lido, nunca alterado, e o processamento roda em ambiente nosso e isolado.
